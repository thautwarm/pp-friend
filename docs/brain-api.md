# Brain API 规格

> **来源**：服务端给出的规范。本文档记录客户端**实际实现**的那部分，
> 以及实现过程中确认的细节。

手机端只做两件事：**采音**和**放音**。识别、对话、合成全部由 brain 承担，
手机上不再有 STT/TTS 引擎。**对话上下文**（它记得什么、聊到哪儿了）全部挂在
`brain_id` 上，手机端不持有。

> **手机端存了一份「展示历史」**（见 §7.2），和上面这句不矛盾：存的是主界面上
> 显示过的那些话，用来重启之后还能往上翻，**不参与任何请求**。
> 删掉本地历史不影响对话，换个 `brain_id` 也不会带出对方的记录。

---

## 0. 端点总览

服务端一共四个，客户端只用前两个：

| 端点 | 请求 | 响应 | 客户端 |
|---|---|---|---|
| `POST /human-to-brain` | `{brain_id, audio}` | `{kind:"text", text}` | ✅ 使用 |
| `POST /brain-to-human` | `{brain_id, skip_before?}` | **前导 + 连续 Ogg 流**（见 §2.2） | ✅ 使用 |
| `POST /agent-to-brain` | `{brain_id, text}` | `{kind:"empty"}` | ❌ 未使用 |
| `POST /brain-to-agent` | `{brain_id}` | `{kind:"empty"}` \| `{kind:"text", text}` | ❌ 未使用 |

后两个是给 agent 的（文本进、文本出），和客户端这套（音频进、音频出）
不是一回事，所以客户端不实现。

> `kind` 在四个端点里是同一个意思：**载荷判别符**。
> `empty` = 没有内容，`text` = 有文本。
> 不用它表达"操作是否成功" —— 那件事由 HTTP 状态码承担。

## 1. 前置约定

### 1.1 `brain_id` —— 人起的名字，不是生成的

**它像人的名字一样有语义**，标识"你在跟哪个 brain 说话"，由用户在客户端配置。

```
brain_id = "员工3"
```

由此推出几件事：

- 客户端只需要一个**文本输入框**，不需要 UUID 生成器，也不需要服务端发号接口
- 状态按名字存在服务端，所以**同一个 `brain_id` 跨 App 重启仍是同一段对话**
- 想开一段全新的对话，就换一个名字
- 它出现在两个请求里，两边必须一致，否则会问到两个不同的 brain

### 1.2 认证 —— Bearer token

两个端点都支持：

```http
Authorization: Bearer <token>
```

- token 由用户在客户端配置（和 `brain_id` 一样是设置项，不是生成的）
- **token 可能为空** —— 即该部署没有启用鉴权。
  客户端在 token 为空时**不发送** `Authorization` 头
  （而不是发一个空的 `Bearer `，那样容易被服务端判成格式错误）

> ⚠️ 401 **不要**当作"网络问题"无限重试 —— 那会把一个配置错误变成持续请求。
> 客户端应当直接提示"token 无效"并**停止轮询**。

## 2. 端点

### 2.1 `POST /human-to-brain`

把一段人类语音交给 brain。**只等转写**。

**请求** —— MessagePack，map：

| 键 | 类型 | 说明 |
|---|---|---|
| `brain_id` | str | 会话句柄 |
| `audio` | **bin** | 人类语音。**Ogg Opus 16kHz**，见 §4 |

**响应** —— MessagePack，map：

```
{ kind: "text", text: string }
```

### 2.2 `POST /brain-to-human`

取 brain 的回复。**长轮询 + 前导 + 一段连续 Ogg Opus 流**：挂到有话要说，
先把整条文本交出来，然后**一边合成一边把音频吐出来**。

**请求** —— MessagePack，map：

```
{ brain_id: string, skip_before?: int }
```

`skip_before` 是可选的 UTC epoch **毫秒**（客户端的钟）。**只在用户打断
AI 说话时设置**，见 §2.3。会话开始、切档案、结束对话都不带。

**响应** —— `Content-Type: application/octet-stream`，body 是：

```
[u32 大端文本长度][UTF-8 文本][1 字节 flags][连续 Ogg Opus 流…]
```

- **文本长度 = 0**：这一轮没有内容。后面没有音频，客户端立刻重发。
  flags 字节仍然存在（客户端按统一格式读取）。
- `flags` 只有 **bit0** 有定义：`1` = 这条是 `skip_before` 跳过的旧消息，
  **body 里没有音频**；其余位保留，必须为 0。
- 文本是这条回复的**原始文本**（`<!-- disable voice -->` 段原样保留，
  那些段只是不产生音频）。**文本一次到齐**，客户端先上屏。
- 音频是**一条连续的 Ogg Opus 流**（采样率见 §4），直接喂流式解码器，
  **不要按块拼文件**。
- **没有结束标记**：body 正常结束 = 说完了。TTS 中途挂掉也是 body 结束，
  客户端不区分二者。
- **一条响应最多一条消息。** 被 `skip_before` 跳过的旧消息一条占一条响应，
  客户端重发来逐条排空。
- 出声之前就失败（音色不存在、TTS 连不上、返回的不是 Ogg）→ **HTTP 502**，
  这条消息放回队列，下一次轮询还能拿到。
- **超时只约束等前导。** 前导到手之后，这条连接可以一直挂到说完，不再受
  客户端那个 120 秒超时影响。没内容时服务端挂到长轮询上限，然后回
  文本长度 0；客户端收到就立刻重发。
- **客户端断开，服务端立即停止后续合成**；已经取走的那条消息不会重投。

### 2.3 `skip_before` —— 用户打断后丢弃打断前排队的内容

**只有用户打断 AI 说话时才带**（开口盖过 AI、通知栏「停止说话」、
音量减键）。会话开始、切档案、结束对话都不带：停着的时候服务端积压的
消息必须原样送达，有文本也有音频。

`skip_before` 之前的 agent 消息**不合成**，而是**一条旧消息一条响应**：
前导里的 `flags` bit0 = 1，文本照常给出，body 随即结束。
客户端把文本**照常显示**在消息流里，并追加进下一次的
`unheard_text`（这些消息确实没有声音）。

客户端的行为是：

1. 用户打断的那一刻记下此刻 `now`，之后每次请求都带 `skip_before: now`。
2. 前导是 `flags bit0 = 1` 就把文本上屏、记进 `unheard_text`，
   然后取消这条流、立刻再发一次（**仍然带同一个 `now`**）。
   一条响应最多排掉一条旧消息。
3. 直到前导不再是 skipped（真回复），把 `skip_before` 清掉，
   后续请求不再带。

打断之后**新入队**的回复时间晚于水位，照常送达 —— 这正是想要的：
打断之前的旧队列丢掉，打断之后的新内容不丢。

> 为什么不做"一条响应排多条 skipped + 跟真回复"：客户端拿到前导就必须
> 决策（上屏、清水位、开始播），让一条响应承载多件事会把这三个动作拆到
> 不同响应上，取消和记账都会变复杂。一条响应只回答一条消息，重发是廉价的。

**不要每次请求都把 `skip_before` 更新成 now** —— 那会把播放期间新积压的
消息一起跳掉。同一个档案同一时刻只有一条 `/brain-to-human`，所以这个水位
只需要一份。

## 3. 载荷编码 —— MessagePack

**不是 JSON，也不是 multipart。** 请求是单个裸的 MessagePack map；
`/brain-to-human` 的响应是「二进制前导 + 原始 Ogg 流」（§3.1），
不是 MessagePack map。

- `Content-Type` / `Accept` 用 `application/msgpack`
  （服务端规范没写明；有些实现用 `application/x-msgpack`。
  客户端把这个值收在 `BrainClient.msgpackContentType` 一个常量里，改一处即可）
- 音频是 MessagePack 的 **bin** 类型，不是 base64、不是字符串
- 二进制原样进出，不经过任何文本编码

> ⚠️ 不要试图把整个响应当 UTF-8 解 —— 前导之后是二进制音频。
> 前导按固定格式切出来，剩下多少字节就原样喂给 Ogg 解码器。

### 3.1 前导格式

`/brain-to-human` 的 body 开头是：

```
[4 字节 u32 大端文本长度][UTF-8 文本][1 字节 flags]
```

- 文本长度**只算 UTF-8 文本本身**，不含 4 字节头和 flags。
- 前导可能被拆进任意多个 TCP/TLS chunk；客户端必须自己累加字节，
  不能假设"一次 read = 前导/一帧音频"。
- 文本长度超过上限（客户端设 8 MiB）是协议错误。
- body 在文本或 flags 中间结束算**截断**，客户端立刻重发，不当作网络
  故障退避。
- **前导之后的所有字节**都是连续 Ogg Opus。解码器自己处理任意切分，
  客户端不能按 HTTP chunk 边界重新组包。
- 等前导超时不是错误：按"这一轮没内容"处理，立刻重发。

客户端用的包：`msgpack_dart`。注意它 pubspec 里写的是 Dart 2 的 SDK 约束
（`>=2.12.0 <3.0.0`）、2023 年后没再更新，但**实测在 Dart 3.13 下可用**
（pub 能正常解析，编解码往返正确）。如果哪天它真的坏了，
备选是自己写一个只覆盖 map/str/bin/int 的最小实现 —— 用到的类型就这些。

## 4. 音频格式

| 方向 | 格式 | 采样率 |
|---|---|---|
| 上行（`/human-to-brain`） | Ogg Opus | **16kHz** |
| 下行（`/brain-to-human`） | Ogg Opus | **24kHz** |

两个方向都是 Ogg Opus，但**采样率不同** —— 跟着两端的模型走：
STT 吃 16k，TTS 出 24k。

下行是**一条连续的 Ogg Opus 流**：客户端增量解析 Ogg page、重组 Opus
packet、逐包解码，把 PCM 追加到播放队列。**不能按 HTTP chunk 边界**
当成一个个独立文件；也不能等整个 body 到齐再解（那样就变回一次性返回）。

纯 Dart 没有可用的 Opus 编解码器，所以两块都走原生：

| 方向 | 客户端做的事 | 原生实现 |
|---|---|---|
| 上行 | PCM16 16k → Opus 编码 → Ogg 封装 | `MediaCodec(audio/opus)` + `MediaMuxer(MUXER_OUTPUT_OGG)` |
| 下行 | 增量 Ogg 解封装 → Opus 解码 → 重采样到引擎速率 | `StreamingOggDecoder`（手写 Ogg 解析）+ `MediaCodec` |

实测：1.5 秒 16k 单声道 PCM16 = 48000 字节，编码后 **5128 字节**（9.4x）。

### 4.1 为什么 minSdk 是 29

| 能力 | 最低 API |
|---|---|
| Opus **解码** | 21 |
| Opus **编码** | **29** |
| `MUXER_OUTPUT_OGG` | **29** |

规范里上行只收 `audio/ogg`，**没有 WAV 回落**。所以 API 24~28 的机器
没有编码器就发不出语音 —— 与其留一个"看起来成功实际失败"的回落分支，
不如把门槛提到 **29（Android 10）**。

按 2026 年 4 月 StatCounter 数据，minSdk 29 覆盖约 91.1% 的设备
（24 是 96.6%）。本项目是自用，这个差别不影响。

> ⚠️ 即使 minSdk 是 29，客户端**仍然在运行时探测编码器**
> （`MediaCodecList` 查有没有 `audio/opus`），不是只判 API 级别 ——
> OEM 差异真实存在。探测失败就明确报错"本机没有 Opus 编码器"，
> 而不是发一个服务端一定拒的格式。

### 4.2 下行解码的采样率陷阱

> ⚠️ **别假设解码出来的采样率等于声明的采样率。**
> Opus 内部固定跑 48kHz，Ogg Opus 头里的 "input sample rate" 只是提示信息。
> Android 的 `MediaCodec` 解码 Opus 通常**直接给 48000Hz**。
> 客户端必须**读解码器实际输出的采样率**再重采样，不能写死 24k ——
> 否则会变速（音调变低、语速变慢），而且很难查。

实测佐证：`MediaCodec` 解出来就是 `48000Hz/1ch`，
再由客户端重采样到引擎的 16000Hz。

## 5. 客户端状态机

```
  开始对话 / 档案开始轮询
     │  skip_before = null（积压照常送达）
     │  用户打断时才设 skip_before = now
     ▼
  ┌─────────────────────────────────────────────┐
  │ POST /brain-to-human                        │
  │ 等前导（只等这一下，超时 → empty）          │
  └──────────────┬──────────────────────────────┘
                 │
      ┌──────────┼───────────────┐
      │          │               │
  文本长度 0   flags bit0 = 1   正常回复
      │          │               │
      │          │               ├─▶ 文本进消息流（只记一次）
      │          │               ├─▶ skip_before = null
      │          │               └─▶ 继续读这条流：
      │          │                     字节 → 流式 Ogg 解码 → 推原生 FIFO
      │          │                     直到 body 正常结束
      ▼          ▼
   立刻重发    文本上屏 + 记进 unheard_text，
             取消后立刻重发（仍带同一个 skip_before）
             —— 一条响应只排一条旧消息

  另一条完全独立的路：
  VAD 切出一句话 ──▶ POST /human-to-brain ──▶ 得到人类文本
```

**同一个档案同一时刻只有一条 `/brain-to-human`。** 不做预取，也不在
Dart 侧排"整条回复"的队列：

- 前导到手就上屏，用户不用等音频合成完。
- 后续音频字节到了就流式解码、推进原生播放队列。**原生 FIFO 就是顺序层**，
  Dart 侧没有第二套播放队列，也没有"取比播快"的积压问题。
- 这条流结束（说完了）之后才发下一次请求。两条回复之间的音频顺序仍由
  原生 FIFO 保证。
- 原生队列里提前压的音频超过 **10 秒**时，客户端暂停读下一块 ——
  TCP 自然背压，服务端也不会把整条回复一口气灌进内存。

> 为什么不再预取：这条响应本身就是"一边合成一边送"，前导延迟已经压到
> 最低；再叠一层预取只会让"同一档案一条流"的约束失效，也让打断时
> 已经到手但没播的整条回复没法处理干净。

### 5.1 重试策略

协议层**没有错误响应** —— 失败只来自网络、HTTP 状态码或截断：

| 情况 | 处理 |
|---|---|
| 等前导超时 | **不是错误**：当作"这一轮没内容"，立刻重发 |
| 网络错误 | 客户端自己退避重试（500ms 起，翻倍，上限 15s），不往外抛 |
| 5xx | 同上（502 = 出声前合成失败，消息已放回队列） |
| 401 / 403 | **不重试**，提示"token 无效"并停止轮询 |
| 文本长度非法 | 报 protocol 错误（重试大概率还是错） |
| 前导中间结束（截断） | **立刻重发**，不走退避；连续 3 次才让 200ms |
| 音频流中途连接中断 | 已播放的照播，不重投（服务端不会重发这条）；这条按"没说完"记账，下次打断时把没听到的尾巴带进 `unheard_text` |

### 5.2 中断在途请求

服务端的 handler 接口带 `options: { signal: AbortSignal }` —— 意思是
**客户端断开连接时，服务端会取消自己正在做的工作**。

客户端据此在结束会话时**主动关掉 HTTP client**，掐掉在途的长轮询。

> ⚠️ `Future.timeout()` **做不到这件事**：它只是停止等待，底层请求照跑。
> 真正中断只能关掉 client（`BrainClient.abort()` 会顺手换一个新的）。
>
> 不这么做的话，每次点「结束对话」都会在服务端留一个挂着的长轮询，
> 直到它自己超时。

实测：点结束后，假 brain 侧收到的请求数**立刻停止增长**（18 秒内保持稳定）。

### 5.3 打断语义

- response 的**文本永远进入消息流**，无论语音是否被打断
- 只有 **AI 语音**会被清空
- **打断默认不做**：收到就播。客户端有一个用户可见的「打断」开关，
  开了之后本地断句一判到人声就停播（不设双讲门槛）；关着时保留一道
  双讲余量门防回声自激 —— 那是防自激，不是自动打断
- 但「判到人声」不等于「刚听到有声那一瞬间」。Silero 一判到有声就
  `speaking = true`，而这个标志会一直扛到收尾那段静音（默认 1000ms）
  结束 —— **跟这段声音本身多长无关**。照它直接打断，咳嗽一声、
  清个嗓子就能把 AI 掐掉。所以客户端还要**连续说够 350ms** 才认，
  中间有一帧掉下阈值就从头数（`bargeInMinSpeechMs`）
- 客户端本地用 `epoch` + `cancel()`：清空播放时 `epoch++`，在途的
  解码/推送看到 epoch 变了就退出，同时取消那条 `/brain-to-human` 流，
  服务端立刻停止后续合成。文本已经进消息流的不会收回。

> ⚠️ **「它还在说话」不能用「Dart 推送循环还在跑」来判。**
> 流式播放时推送循环是"来一块推一块"，但 AudioTrack 里仍可能压着好几秒
> 还没响完的音频；循环退出不代表声音停了。判据必须是**原生缓冲里还有
> 没有没响完的帧**，双讲门同理。

### 5.3b 「我没听到」的上报：`unheard_text`

被打断（或手动清空播放）之后，客户端要告诉 brain「你哪一段我没听到」。

**主题是文字，不是时间。** brain 真正需要的是"哪几个字没进用户的耳朵"，
一个毫秒数对它没用 —— 它还得自己把文本和音频对齐。所以协议让客户端
把**没被听到的那部分文字**直接发回去。对话两边的认知就是这么对齐的：
不带的话，brain 以为自己讲完了，下一轮接着「刚才说的那个」往下讲，
用户只能装懂。

#### 文本和音频的对应关系只能靠估

新协议不再提供句子表，也没有 `consumed_sentences`。前导给的是**整条
文本**，后面是一条连续音频流，客户端不知道每个采样对应哪个字。

被打断时，客户端按比例估：

```
已听到比例 = 播放头走过的采样数 / 已经推进原生队列的采样数
```

去乘剥过 `<!-- disable voice -->` 的正文长度，估出断在第几个字，再按
句子边界取整。

#### 两种情况取整方向不同

- **音频流已经结束**（整条都推送完了）：估出来的位置往后找最近的句界。
  落在一句中间就整句算听到 —— 只有明确没开始的句子才记进没听到。
- **音频流还没结束**（还在合成/下载，被打断）：后面还有多少音频、对应
  多少字都不知道。估出来的位置**往前收到当前这句的开头**，整句算没
  听到。宁可多报，也不能让 brain 以为用户听过它还没说出口的话。

> 中文一个字一个字长短差很多，纯比例并不精确。估错的代价被限制在
> 一句以内，并且总是偏向"少算听到"。

#### 上报的字段

| 字段 | 类型 | 含义 |
|---|---|---|
| `unheard_text` | str | **规格内的可选字段**：没被听到的那部分文字 |
| `heard_ms` | int（毫秒） | 客户端附带，**仅供诊断，不在本规格里**；服务端应忽略未知字段 |

- `unheard_text` = **正在播的那一条没听完的尾巴**（按上一节估）++
  **后面已经入站但还没播的整条回复**。还没入站、客户端根本不知道的
  内容不算。
- 它是**累加**的，不是"只报最后一次"。一次打断只处理到当时已经入站的
  内容；之后如果还有内容入站，也会继续追加，直到下一次上传成功才清。
- **只在上一段被打断/清空时才出现。** 没被打断就不带 `unheard_text` ——
  "没带"和"空字符串"是两件事，别用空串冒充缺失。`heard_ms` 最多作为
  诊断值附在旁边，不能当协议字段依赖。
- 挂在下一句用户的话上，而不是当场单独发一条：协议里没有汇报端点，
  而且它天然属于下一句的上下文。客户端在请求**成功后**才清掉它，
  失败就留着 —— "你漏了一段"迟到也比丢了好。
- `skip_before` 跳过的旧消息**文本会显示在消息流里**（没有音频），
  同时按顺序追加进 `unheard_text` —— 用户确实没听到，下一轮该让
  brain 知道。文本不能悄悄吞掉。
- brain 端拿到之后怎么办（当场重说 vs 后续避开）**待定**，见
  `需求-闭麦与打断.md` 待定清单第 3 条。

### 5.4 清空播放的触发方式

| 触发 | 覆盖场景 | 实现 |
|---|---|---|
| 通知栏「停止说话」按钮 | 后台、锁屏 | 前台服务的一个 action |
| 音量减键 | App 前台时 | `MainActivity.onKeyDown`，**仅在正在播 AI 语音时拦截** |

两者和「开口盖过 AI」一样，都算**打断**：客户端在那一刻设下
`skip_before`，打断之前排队的旧消息不再送（文本仍上屏、记进没听到）。
目前没有"只跳过当前这一条、继续读下一条"的交互 —— 那是另一种行为，
入口待定。

> 前台服务区分了三种停止动作，不能混用：
> `ACTION_STOP`（Dart 程序化停止，**不发事件**）、
> `ACTION_STOP_FROM_NOTIFICATION`（通知栏「结束」，发 `endRequested`）、
> `ACTION_CLEAR`（通知栏「停止说话」，发 `clearPlaybackRequested`）。
> 混用会让程序化停止也发出 `endRequested`，进而让 `stop()` 重入。

音量键的局限：`onKeyDown` 只在 App 处于前台时收到事件，后台/锁屏收不到 ——
那个场景由通知栏按钮覆盖。只在播放时拦截是为了不吞掉正常的音量调节。

## 6. 客户端实现要点

| 项 | 说明 |
|---|---|
| VAD 在本地 | 必须。否则得把整条麦克风流实时推上去，那是另一套协议 |
| 静音判定时长 | 客户端唯一能优化的延迟项，默认 1000ms，可配 |
| `/human-to-brain` 串行队列 | 切句和网络往返是两个速度，并发发出去顺序就乱了。队列上限 8 句 |
| `/brain-to-human` 单流 | 每个档案同一时刻只有一条流，不预取、不排整条回复 |
| 下行解码 | 增量解析一条连续 Ogg 流，PCM 直接推原生 FIFO；不按 HTTP chunk 重组 |
| 原生缓冲上限 | 提前压超过 10 秒就暂停读下一块，靠 TCP 背压 |
| 音频不落盘 | 全程 PCM 流，不涉及容器/编码格式选型 |
| 消息流上限 | 内存窗口 300 条，盘上（§7.2）不限 |
| 事件日志上限 | 120 条 |

### 6.1 调试入口

brain 没起时也要能验证音频链路，所以有两个不依赖 brain 的入口：

- **播放测试音（AEC 自测）** —— 循环播放类语音测试音，
  看麦克风电平条是否接近静默。这是判断 AEC 的唯一手段
- **发送测试语音** —— 把一段测试音当成你说的话走完整条上行链路
  （编码 → 上传 → 文本回流）。不需要麦克风就能验证上行

## 7. 档案（profile）与本地历史

一个**档案** = 一套 brain 配置（baseUrl / brain_id / token）+ 一份独立的本地
历史 + 一个头像和主题色。用途是"同时跟几个 brain 保持联系"。

### 7.1 同一时刻只有一个在完整交互

音频（麦克风、扬声器、前台服务）在整机上都只有一份。所以"多个档案同时跑"
的准确意思是**每个档案各有一条 `/brain-to-human` 流**（一个档案同一
时刻仍然只有一条）：

| 状态 | 轮询 | 上行 | 播放 | 记历史 |
|---|---|---|---|---|
| 聚焦 | 跑 | 跑 | 播 | 记 |
| 未聚焦但开着 | 跑 | 不跑 | 收到即丢 | 记（只有文字） |
| 关闭 | 不跑 | 不跑 | 不播 | 不记 |

未聚焦的档案收到回复时，**前导的文字照记，然后立刻取消这条流** ——
音频根本不下载。这是刻意的：切过去时你应该看得到它说过什么，但不该被
另一个 brain 的声音打断，也没必要为不播的音频占带宽和合成资源。

切换档案**立刻停掉正在播的声音**。上一个档案没听完的那一段，按 §5 的
`heard_ms` / `unheard_text` 机制记在**它自己**账上，下次跟它说话时带给它，
不会串到新聚焦的那个档案上。

### 7.2 本地历史是「展示历史」，不是对话上下文

```
<应用文档目录>/pp_friend/
├── history/<档案id>/000001.jsonl     # 一行一条，只增不删
├── history/<档案id>/000002.jsonl     # 每满 1MB 换一个
└── avatars/<档案id>_<时间戳>.<ext>
```

- **一行一条 NDJSON**，每满 1MB 换下一个文件（约 4~6 千条）。显示最近一屏
  只读最后一个文件。**往上翻一页要从最新那片往回扫**（没有索引，逐行解析
  才知道 `beforeSeq` 之前是哪些），一页的代价随"离最新有多远"线性增长，
  几十万条之后翻一页是几十毫秒的同步解析 —— 要优化就是按 seq 猜片子再二分，
  现在没做
- 只记 `role` / `text` / 时间。**不存音频，也不存「没听到」的标记** ——
  那是协议字段，不是消息
- **删掉本地任何内容都不影响对话**：上下文始终在 brain 那边
- **永久保留，没有自动清理。** 一条中文消息 JSON 后约 200 字节，一天两千条
  约 400 KB，一年约 150 MB。设置页显示占用并提供清空，不做自动删除
- 删档案**不删历史**（那是用户的东西），但会删掉它的头像文件

崩溃、或者一次写到一半失败（磁盘满），都可能留下半行（没有结尾换行）。
读的时候跳过这一行；写的时候**每次追加前都看一眼文件最后一个字节**，不是
换行就先补一个 —— 否则新写的那条会接在半行屁股后面，和它合成同一个物理行，
永远读不出来。用缓存记住"上次检查时尾巴是干净的"是不行的：半行恰恰是那之后
一次失败的写留下的。
