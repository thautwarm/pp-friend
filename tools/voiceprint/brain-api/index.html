Brain API

手机只采音和放音；识别、对话、合成都由 brain（你自己的服务端）承担。这一页是协议本身，照着就能写一个自己的 brain。

与仓库里的 docs/brain-api.md 同源，以它为准。

概览

协议里一共四个端点，客户端只用前两个。后两个是给 agent 的纯文本通道，和客户端这套音频进、音频出不是一回事。

端点 请求 响应 客户端
POST /human-to-brain {brain_id, audio} {kind:"text", text} 使用
POST /brain-to-human {brain_id} {kind:"empty"} | {kind:"text", text, audio} 使用
POST /agent-to-brain {brain_id, text} {kind:"empty"} 未使用
POST /brain-to-agent {brain_id} {kind:"empty"} | {kind:"text", text} 未使用

kind 是载荷判别符：empty 是没有内容，text 是有文本。它不代表操作成败，那是 HTTP 状态码的事。

客户端跑两条互相独立的循环：一条在 /brain-to-human 上长轮询，挂住直到 brain 有话说；另一条把断句切出来的语音按顺序串行发到 /human-to-brain。

鉴权

两个端点都支持 Bearer token：

Authorization: Bearer <token>
  • token 是用户配置项，和 brain_id 一样，不是生成的。
  • token 可以为空，表示这个部署没开鉴权。空的时候客户端不发 Authorization 头，而不是发一个空的 Bearer。
  • 401 是配置错误，不要当网络问题无限重试。提示 token 无效，停掉轮询。

载荷编码：MessagePack

请求和响应都是裸的 MessagePack，不是 JSON，也不是 multipart。上行音频放在 map 里，类型是 bin：不是 base64，不是字符串，二进制原样进出。

  • Content-Type / Accept 用 application/msgpack。规范没写明这个取值，客户端把它收在一个常量里，改一处即可。
  • 不要把响应当 UTF-8 解，里面是二进制音频。先按 MessagePack 解出 map，再取字段。

POST /human-to-brain

把一段人类语音交给 brain，只等转写。断句切出一句话就发一次。请求是一个 MessagePack map：

键 类型 说明
brain_id str 会话句柄，人起的名字，比如 "员工3"。两个端点里必须一致。
audio bin 整句语音，Ogg Opus 16 kHz。没有 WAV 回落。
heard_ms int 可选。上一段回复实际被听到的毫秒数，见「打断记账」。
unheard_text str 可选。上一段回复没被听到的那部分文字，见「打断记账」。

响应：

{ "kind": "text", "text": "..." }

POST /brain-to-human

长轮询：请求挂住，直到 brain 有话说或者超时。请求只有 brain_id 一个字段。响应是两种之一：

{ "kind": "empty" }

{ "kind": "text",
  "text": "...",
  "audio": <bin: Ogg Opus 24kHz>,
  "spans": [ { "text": "...", "ms": 1200 }, ... ] }
  • empty 只是「暂时没话说」，客户端立刻再发一次，不停不等。
  • spans 是可选的按句时间账，用来支持「哪几句没听到」的上报。不给也能用，只是被打断时客户端只能估一个断点。

音频格式

方向 格式 采样率
上行 /human-to-brain Ogg Opus（audio/ogg） 16 kHz
下行 /brain-to-human Ogg Opus（audio/ogg） 24 kHz
  • 两个方向采样率不同，是跟着模型走的：识别吃 16 kHz，合成出 24 kHz。
  • 实现时注意：Opus 内部固定跑 48 kHz，解码出来的采样率未必等于声明的采样率。要读解码器的实际输出再重采样，写死会变速。

打断记账：heard_ms 与 unheard_text

brain 说到一半被打断，客户端要告诉它「哪一段没进到用户耳朵里」。报的是文字不是时间点：光给一个毫秒数，brain 还得自己把文本和音频对齐。

所以回复里可以带一份按句的时间账 spans。它顺序拼起来就是整条音频，句间不许有没记账的静音：

键 类型 说明
spans[].text str 这一小段的文字，按句切最好。
spans[].ms int 这一小段在 audio 里占的毫秒数。

spans 是可选的。没给、或格式不对，客户端按 heard_ms / 总长 的比例估断点，再对齐到最近的句子边界。

被打断之后，下一句 /human-to-brain 多带两个字段：

  • unheard_text：没听到的那部分文字，包括正在播的那条没听完的尾巴，加上播放队列里还没轮到播的整段。
  • heard_ms：实际听到的毫秒数，纯粹方便服务端诊断。
  • 只在真的被打断过才出现。没打断就一个键都不发：「没值」和「听到了 0 ms」是两件事。
  • 账是累加的，挂在下一句用户的话上一起走，上传成功才清，失败留着。

错误与重试

协议层没有错误响应，失败只来自网络和 HTTP 状态码：

情况 处理
网络错误 / 超时 / 5xx 客户端退避重试：500 ms 起，翻倍，15 s 封顶。
401 / 403 不重试。提示 token 无效，停止轮询。
响应不是合法 MessagePack 协议错误，重试大概率还是错。

最小示例

字段名就这些。一个能跑的 brain 只需要接两种请求、回三种 map。仓库里有一个按这个协议手写的假 brain（tools/mock_brain.py，含一份独立的 MessagePack 实现），可以拿来对照。

POST /human-to-brain
Content-Type: application/msgpack
Authorization: Bearer <token>   (optional)

{ "brain_id": "员工3", "audio": <bin> }

# interrupted last time:
{ "brain_id": "员工3", "audio": <bin>,
  "heard_ms": 1320, "unheard_text": "..." }

# response:
{ "kind": "text", "text": "..." }
POST /brain-to-human
Content-Type: application/msgpack

{ "brain_id": "员工3" }

# nothing to say:
{ "kind": "empty" }

# something to say:
{ "kind": "text", "text": "...", "audio": <bin>,
  "spans": [ { "text": "...", "ms": 1200 },
             { "text": "...", "ms": 900 } ] }

  • brain 收到 unheard_text 之后怎么处理（当场重说还是以后避开）还没定。
